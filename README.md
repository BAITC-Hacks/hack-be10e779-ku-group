# ВетроПрогноз — агентный прогноз выработки ВЭС на 24–48 часов

ВетроПрогноз помогает диспетчеру или аналитику ВЭС оценить почасовую нормированную выработку станции на следующие двое суток. Для каждого часа система возвращает медианный прогноз `p50`, интервал неопределённости `p10–p90`, прогнозы двух турбин, пояснение агента и карточки внимания. Основной сценарий работает без личного аккаунта, API-ключа и доступа к интернету: архивные выпуски погоды сохранены в `data/weather/`, а режим DEMO выполняет тот же цикл детерминированным планировщиком (`backend/app/forecast/agent.py`, `backend/app/forecast/weather.py`).

## Назначение и соответствие задаче

Решение строит ретроспективные выпуски за 31.01–27.02.2026 для почасовой выработки 01–28.02.2026. Один выпуск содержит 24 часа D+1 и 24 часа D+2; значения ограничены диапазоном 0–1, потому что номинальная мощность станции в МВт в исходных данных не дана (`CASE.md`, `backend/app/forecast/pipeline.py`).

| Возможность | Где реализована | Как проверить |
| --- | --- | --- |

| Только доступные на момент решения архивные выпуски погоды | `backend/app/forecast/weather.py`, `backend/app/forecast/model.py` | `cd backend && pytest -q tests/test_forecast_core.py` |

## Ценность для Казахстана

- Производитель ВИЭ подаёт заявку с почасовыми объёмами поставки до 08:00 по времени Астаны в сутки, предшествующие операционным суткам: пункт 9 правил, утверждённых [приказом Министра энергетики РК от 2 марта 2015 года № 164](https://adilet.zan.kz/rus/docs/V1500010662). Прогноз D+1 даёт основу для такой заявки, а D+2 — раннее предупреждение (`backend/app/forecast/pipeline.py`).
- Дисбаланс определяется как разница планового и фактического сальдо за каждый час операционных суток: пункт 78 [Правил функционирования балансирующего рынка электрической энергии](https://zakon.uchet.kz/rus/docs/V1500010532). Поэтому продукт показывает именно почасовой прогноз и выделяет часы существенного пересмотра (`backend/app/forecast/passport.py`, `frontend/src/features/forecast/`).
- По данным [годового отчёта KEGOC за 2024 год](https://ar2024.kegoc.kz/ru/electricity-balance.html), в Казахстане действовали 57 ВЭС суммарной мощностью 1 525,7 МВт. Задача точного планирования относится уже к значимому для энергосистемы классу генерации.

## Архитектура

```text
дата выпуска D, 23:59 UTC+5
          │
          ▼
1. rank_weather_sources ── качество и полнота источников
          │
          ▼
2. fetch_weather ───────── только уже опубликованные выпуски
          │
          ▼
3. build_features ──────── признаки и ансамбль погоды
          │
          ▼
4. run_forecast ────────── p10 / p50 / p90, T1 / T2, калибровка
          │
          ▼
5. validate_forecast ───── 48 ч подряд, [0,1], p10 ≤ p50 ≤ p90, правило публикации погоды; откат на кривую мощности
          │
          ▼
6. analyze_forecast ────── пики, провалы, неопределённость
          │
          ▼
7. compare_with_previous ─ сохранённый D+2 вчера ↔ D+1 сегодня
          │
          ├── паспорт и неизменяемая версия выпуска
          └── карточки внимания диспетчера и журнал шагов
```

Все семь инструментов объявлены и собраны в `TOOLS` в `backend/app/forecast/agent.py`:

| Инструмент | Решение |
| --- | --- |
| `rank_weather_sources` | оценивает MAE источников на последних доступных 30 сутках и пропуски в окне прогноза |
| `fetch_weather` | получает архивный прогноз, исключает выбранные источники и проверяет время публикации |
| `build_features` | строит 48 строк признаков и пересчитывает статистики ансамбля без исключённых источников |
| `run_forecast` | запускает квантильные модели и применяет конформную поправку к `p10–p90` |
| `validate_forecast` | проверяет результат перед выдачей: 48 часов подряд, значения в [0, 1], порядок `p10 ≤ p50 ≤ p90`, выпуск погоды каждого часа по правилу публикации; нарушение исправляет (откат на кривую мощности, восстановление порядка) и показывает в отчёте. Если LLM не вызвала проверку — код вызывает её перед выдачей |
| `analyze_forecast` | проверяет правдоподобие, находит пик, часы низкой выработки и признаки высокой неопределённости |
| `compare_with_previous` | сравнивает текущий D+1 с сохранённым D+2 предыдущего выпуска для тех же 24 часов |

Есть два режима исполнения (`backend/app/forecast/agent.py`, `backend/app/ai/llm.py`):

- **LIVE** — LLM через function calling выбирает последовательность вызовов и исключает источник погоды с пропусками в окне прогноза; при незавершённом цикле срабатывает детерминированный планировщик.
- **DEMO** — тот же цикл и правила выбора источников выполняет детерминированный планировщик без ключа.

LLM не рассчитывает прогнозные значения. Признаки, квантили, метрики, калибровку, сравнение выпусков и пороги карточек считает Python-код (`backend/app/forecast/model.py`, `backend/app/forecast/calibrate.py`, `backend/app/forecast/passport.py`); агент управляет вызовами и формирует объяснение только из результатов инструментов (`backend/app/forecast/agent.py`).

## Честность по времени и источник погоды

Погода получена из [Open-Meteo Previous Runs API](https://open-meteo.com/en/docs/previous-runs-api); данные распространяются по [CC BY 4.0](https://open-meteo.com/en/license), источник не требует ключа. В ансамбль входят семь источников: `best_match`, `ecmwf_ifs025`, `icon_global`, `gfs_seamless`, `jma_seamless`, `cma_grapes_global`, `gem_seamless` (`backend/app/forecast/weather.py`).

Для каждого целевого часа `h` код выбирает минимальное `N` из 1, 2 или 3, для которого выпуск уже был доступен в момент решения:

```text
h − N суток + 7 часов ≤ дата выпуска D, 23:59
```

Семь часов — консервативная задержка публикации NWP-выпуска. Поэтому D+1 не означает механически `previous_day1` для всех 24 часов: для выпуска 09.02.2026 используются 17 часов выпуска за одни сутки, 24 часа выпуска за двое суток и 7 часов выпуска за трое суток. Это правило реализовано в `backend/app/forecast/model.py::run_lead`, а выбранные выпуски и результат проверки входят в `time_integrity` и паспорт (`backend/app/forecast/agent.py`, `backend/app/forecast/passport.py`).

Тест `test_every_weather_run_used_was_published_before_issue_time` перебирает каждый использованный выпуск и требует, чтобы время его публикации не было позже `issued_at` (`backend/tests/test_forecast_core.py`). Фактическая погода прогнозируемых суток и реанализ в признаках не используются.

## Паспорт выпуска, версии и карточки

Каждый завершённый выпуск сохраняется как `outputs/forecasts/<forecast_id>.json`. Паспорт содержит момент решения и целевой интервал в UTC+5, погодный профиль и использованные выпуски, эффективные и исключённые источники, границы обучающих данных, версии модели и калибровки, `input_hash`, `result_hash`, режим исполнения и статус проверки доступности входов (`backend/app/forecast/passport.py`).

`forecast_id` составлен из даты и хеша входов. Повтор с теми же входами даёт тот же `forecast_id`; существующая версия не перезаписывается (`backend/app/forecast/passport.py::save`). Ссылка `parent_id` связывает выпуск с предыдущим сохранённым выпуском.

При сравнении берутся общие 24 часа: вчерашний сохранённый D+2 и сегодняшний D+1. Прошлый прогноз не пересчитывается новой моделью; реконструкция применяется только тогда, когда сохранённой предыдущей версии нет, например для первого выпуска 31.01 (`backend/app/forecast/agent.py::compare_with_previous`, `backend/app/forecast/passport.py::compare`).

В `passport.cards` формируются проверяемые карточки для диспетчера (`backend/app/forecast/passport.py::cards`):

- «Существенный пересмотр» — часы, где `|p50 новый − p50 прошлый| ≥ 0,10`;
- «Широкий диапазон» — часы, где `p90 − p10 ≥ 0,30`;
- «Ненадёжный вход» — нарушение временной проверки или пропуски погоды.

Карточки, паспорт, график, почасовая таблица и журнал инструментов показаны на вкладке прогноза (`frontend/src/features/forecast/`).

## Данные и модель

Организатор предоставил `data/raw/turbine1.csv` и `data/raw/turbine2.csv`: 10-минутные измерения с 11.03.2023 по 31.01.2026. Час считается полным при наличии всех шести точек; выработка станции — средняя нормированная мощность двух турбин (`backend/app/forecast/data.py`). Факта за февраль 2026 года в исходных данных нет.

Модель — `HistGradientBoostingRegressor` для `p10`, `p50`, `p90` и двух турбин. Признаки включают доступную на момент выпуска погоду, горизонт, календарные признаки и значения/разброс ансамбля; квантили упорядочиваются и ограничиваются диапазоном 0–1 (`backend/app/forecast/model.py`). Базовые методы для сравнения — эмпирическая кривая мощности и персистентность (`backend/app/forecast/model.py`).

## Качество прогноза

Источник таблицы — `outputs/metrics.json`. Проверка выполнена скользящим окном по октябрю 2025 — январю 2026: для каждого месяца обучение заканчивается до его начала (`backend/app/forecast/model.py::holdout_metrics`). Так как мощность уже нормирована к номиналу 0–1, **nMAE = MAE × 100% номинала**, а nRMSE — RMSE × 100% номинала.

| Горизонт | Метод | Часов | nMAE, % номинала | nRMSE, % номинала |
| --- | --- | ---: | ---: | ---: |
| D+1 | Модель, бустинг и ансамбль погоды | 2 885 | 14,90 | 22,25 |
| D+1 | Проверка B1: модель без `gfs_ws100` (худший источник по ошибке ветра) | 2 885 | 14,95 | 22,25 |
| D+1 | Кривая мощности | 2 885 | 18,17 | 26,95 |
| D+1 | Персистентность | 2 846 | 35,55 | 47,50 |
| D+2 | Модель, бустинг и ансамбль погоды | 2 885 | 16,09 | 23,75 |
| D+2 | Проверка B1: модель без `gfs_ws100` (худший источник по ошибке ветра) | 2 885 | 16,14 | 24,00 |
| D+2 | Кривая мощности | 2 885 | 19,30 | 28,34 |
| D+2 | Персистентность | 2 826 | 37,34 | 48,95 |

**Проверка решения агента (B0/B1).** Исключение источника с худшей ошибкой ветра (`gfs_ws100`) не улучшает прогноз мощности
(D+1: 14,95 % против 14,90 %) — модель сама учитывает качество источников. Поэтому агент исключает источник только при пропусках
в окне прогноза (`backend/app/forecast/agent.py::_deterministic`), и строка «Модель, бустинг и ансамбль погоды» описывает именно
то, что выполняет агент. Граница обучения каждого месяца проверки — S − 1 сут − 1 ч, чтобы и прогноз на D+2 для первого числа
не видел «будущий» факт.

Для контекста, обзор Giebel et al. приводит для day-ahead прогноза отдельной ВЭС отраслевой диапазон **10–20% nRMSE от номинальной мощности** ([стр. 59 отчёта](https://backend.orbit.dtu.dk/ws/files/128933990/GGiebelEtAl_StateOfTheArtInShortTermPrediction_ANEMOSplus_2011.pdf)). Наши 22,25% для D+1 и 23,75% для D+2 находятся выше этого ориентира; сравнение ориентировочное, поскольку площадки, периоды и доступные входы различаются.

Некалиброванный интервал `p10–p90` в том же скользящем holdout покрывает 69,2% факта для D+1 и 67,9% для D+2 при цели 80% (`outputs/metrics.json`). Отдельная калибровка обучена на октябре–декабре и проверена на январе.

Интервал `p10–p90` калибруется методом split-conformal CQR отдельно по режимам ветра (`backend/app/forecast/calibrate.py`, `outputs/calibration.json`):

| Проверка на январе 2026 | До калибровки | После калибровки | Цель |
| --- | ---: | ---: | ---: |
| Покрытие `p10–p90` | 66,5% | 77,5% | 80,0% |
| Средняя ширина интервала | 0,445 | 0,477 | — |

Калибровка улучшила покрытие, но не достигла целевых 80%; это отражено в известных ограничениях.

### Что проверили и не взяли

Эксперимент воспроизводится кодом `backend/experiments/features_exp.py`, выводы зафиксированы в разделе «Эксперимент признаков» файла `docs/memory/backend.md`. Критерий принятия: снижение MAE `p50` минимум на 0,002 в каждом или как минимум в трёх из четырёх месяцев holdout.

| Кандидат | Результат | Решение |
| --- | --- | --- |
| Плотность воздуха `ρ = p/(287,05·T)` | не дала устойчивого улучшения MAE | не брать |
| `ρ·ws100³` | не дала устойчивого улучшения MAE | не брать |
| Ветер на высотах 80 и 120 м | не дал устойчивого улучшения MAE | не брать |
| Вес свежих наблюдений `0,5^(возраст/180)` | улучшил только два месяца и ухудшил январь | не брать |
| Все признаки вместе | не прошли критерий | не брать |

## Установка и запуск

Требуются Docker 24+ и Docker Compose v2. Для первой сборки нужен интернет, чтобы получить базовый образ и зависимости; после сборки основной DEMO-сценарий использует локальный погодный архив.

```bash
cp .env.example .env
docker compose up --build
```

Откройте <http://localhost:8000>. FastAPI отдаёт собранный frontend с того же порта (`Dockerfile`, `backend/app/main.py`). При первом старте модель обучается в фоне; состояние `model` в `GET /health` меняется на `ready` (`backend/app/main.py`).

Локальный запуск backend для разработки:

```bash
cd backend
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-dev.txt
.venv/bin/uvicorn app.main:app --reload --port 8000
```

Для frontend нужны Node.js 20+ и npm:

```bash
cd frontend
npm ci
npm run dev
```

## Переменные окружения

Приложение запускается и без `.env`: значения по умолчанию заданы в `backend/app/config.py`, пример — в `.env.example`.

| Имя | Назначение | По умолчанию | Обязательна |
| --- | --- | --- | --- |
| `APP_MODE` | `demo` — планировщик; `live` — LLM выбирает инструменты | `demo` | нет |
| `LLM_API_KEY` | ключ OpenAI-совместимого API для LIVE | пусто | только для LIVE |
| `LLM_MODEL` | модель живого агента | `gpt-5.4-mini` | нет |
| `LLM_BASE_URL` | адрес OpenAI-совместимого API; пусто означает OpenAI | пусто | нет |
| `APP_PORT` | порт приложения на хосте | `8000` | нет |
| `BUILD_COMMIT` | SHA сборки в `/health` | `dev` | нет |

Если выбран `live`, но ключ отсутствует или LLM недоступна, прогноз завершается DEMO-планировщиком (`backend/app/forecast/agent.py`, `backend/app/ai/llm.py`). Секреты нельзя коммитить; `.env` исключён через `.gitignore`.

## Проверка основного сценария

После `docker compose up --build` из второго терминала запустите:

```bash
./scripts/smoke.sh
```

Smoke ждёт прогрева модели, строит выпуск на 09.02.2026, проверяет 48 часов и честность по времени, требует шаги агентного цикла, проверяет ошибку для даты вне периода, метрики, историю и главную страницу (`scripts/smoke.sh`). Успешный итог: `Smoke пройден`.

Ручной запрос:

```bash
curl -X POST http://localhost:8000/api/forecast \
  -H 'Content-Type: application/json' \
  -d '{"issue_date":"2026-02-09"}'
```

В ответе должны быть 48 элементов `hours`, `time_integrity.ok: true`, семь инструментов в `steps`, `passport` и `cards` (`backend/app/api/forecast.py`, `backend/app/forecast/agent.py`).

## Воспроизведение бэктеста и метрик

Команды выполняются из `backend` в установленном Python-окружении:

```bash
python -m app.forecast.cli backtest
python -m app.forecast.cli metrics
```

`backtest` выполняет 28 выпусков через `agent.run(planner_only=True)` и создаёт `outputs/forecast_feb2026.csv` на 1 344 строки и `outputs/forecast_feb2026_final.csv` на 672 наиболее свежих D+1-значения (`backend/app/forecast/cli.py`). `metrics` воспроизводит скользящую проверку и обновляет `outputs/metrics.json` (`backend/app/forecast/model.py`).

Обновление погодного архива требует интернет-соединения и выполняется отдельно:

```bash
python -m app.forecast.cli weather
```

Для штатной проверки эта команда не нужна: семь ответов Previous Runs уже сохранены в `data/weather/` (`backend/app/forecast/weather.py`).

## API

Контракт и схемы описаны в `docs/api-contract.md`, реализованные маршруты находятся в `backend/app/api/forecast.py` и подключены с префиксом `/api` в `backend/app/main.py`.

| Метод и путь | Назначение |
| --- | --- |
| `GET /health` | режим, SHA сборки и состояние прогрева модели |
| `GET /api/meta` | период истории, тестовый период, турбины и сохранённые выпуски |
| `POST /api/forecast` | построить и сохранить выпуск для `issue_date` |
| `GET /api/forecast/{issue_date}` | получить последнюю сохранённую версию выпуска |
| `GET /api/backtest` | получить готовый февральский бэктест |
| `POST /api/backtest` | запустить полный бэктест 31.01–27.02 |
| `GET /api/backtest/csv?kind=all\|final` | скачать полный или финальный CSV |
| `GET /api/metrics` | метрики holdout, покрытие и калибровка |
| `GET /api/history?start=…&end=…` | получить исторический факт, не более 62 дней |
| `GET /api/holdout?issue_date=…` | прогноз против факта для январского выпуска |

Асинхронные `POST /api/jobs/forecast` и `GET /api/jobs/{job_id}` отмечены в `docs/api-contract.md` как P1, но в текущую версию не входят.

## Известные ограничения

- Фактическая выработка за февраль 2026 года не предоставлена, поэтому локально нельзя посчитать качество на тестовом месяце (`CASE.md`, `backend/app/forecast/data.py`).
- Выработка нормирована 0–1; без номинальной мощности станции результат нельзя корректно перевести в МВт (`CASE.md`).
- У турбины 1 есть крупный разрыв исходных данных в мае–июле 2024 года; неполные часы исключаются (`backend/app/forecast/data.py`).
- После калибровки покрытие `p10–p90` на январе составляет 77,5% при цели 80% (`outputs/calibration.json`).
- Модель обучена для двух заданных турбин и одной точки; перенос на другую ВЭС требует её истории и повторной проверки (`backend/app/forecast/data.py`, `backend/app/forecast/model.py`).
- LIVE зависит от внешнего LLM API; DEMO и все численные расчёты работают без него (`backend/app/forecast/agent.py`).
- Пороги карточек 10 п.п. и 30 п.п. — демонстрационные настройки команды, а не нормативные значения (`backend/app/forecast/passport.py`).

## Как использованы AI-инструменты

При разработке использовались Claude Code (Максим и Оксана) и OpenAI Codex (Владимир). В продукте LIVE-агент через function calling выбирает инструменты и источники, а DEMO-планировщик обеспечивает воспроизводимую проверку без ключа (`backend/app/forecast/agent.py`, `backend/app/ai/`). Прогнозная математика полностью находится в обычном коде и не подменяется сохранённым текстом LLM (`backend/app/forecast/model.py`, `backend/app/forecast/calibrate.py`).
