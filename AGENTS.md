## Жёсткие правила

- **Никаких секретов в репозитории.** Ключи только в `.env` (в `.gitignore`); в репе — `.env.example` без значений.
- **Историю не переписываем:** запрещены `git push --force`, `rebase` уже запушенных коммитов, `commit --amend` после push, squash. История проверяется организаторами.
- Разработка только в этом репозитории. Ничего не переносим готовым куском извне.
- Всё заранее созданное и всё стороннее (библиотеки, модели, датасеты, шаблоны) вносится в раздел раскрытия в README с источником
  и назначением (п. 5.4.4). Заготовки — только инфраструктура, шаблоны и инструменты; основная функциональность Задачи создаётся
  13:00–18:00 (п. 5.4.4.2); готовое ядро, уже решающее Задачу, использовать нельзя (п. 5.4.5).
- Синтетические и демо-данные честно помечаются как синтетические — в данных, в UI и в README.
- Не выдумывать факты, нормы, цифры, ссылки на документы. Нет источника — так и написать.
- Никаких атак, сканирования и вмешательства в чужие системы.
- README — **только на русском**. Сообщения коммитов — на русском.
- Любые AI-инструменты разрешены; Codex обязателен, **только если это требует ТЗ Задачи** (п. 5.4.12) — проверить при разборе.
  По умолчанию в продукте OpenAI API и агентный подход (модель вызывает инструменты); Владимир работает в Codex; всё это описано в README.
- Права на Результаты: организатор получает безвозмездное бессрочное право использования, включая модификацию и передачу
  третьим лицам (п. 6.1). В проект не попадает то, что нельзя передать на таких условиях.

## Как работаем

- **Один полностью работающий P0-сценарий end-to-end важнее любого числа фич.** Сначала грубый сквозной проход (UI → API → логика → результат), потом улучшения.
- Приоритеты: **P0** — обязательные требования кейса; **P1** — усиливает демо (деплой на свой сервер, затем MCP / ChatGPT App); **P2** — только на словах в README как развитие. P1 не начинаем, пока P0 не проходит smoke.
- Простое решение лучше «правильного». Без преждевременных абстракций, без новых зависимостей без нужды, без рефакторинга ради красоты.
- Критерии и веса — из ТЗ; пока ТЗ их не задаёт, ориентир — прежняя таблица 25/20/20/20/15 (`docs/hackathon-rules.md`): README,
  воспроизводимость и соответствие кейсу — 60 из 100, и они же теперь условия допуска. README обновляется **вместе с кодом**, а не в конце.
- **Проверка без наших аккаунтов (п. 5.6.6):** ключевая функциональность проверяется без личных аккаунтов и подписок участников.
  Внешние API допустимы (п. 5.4.12.1), но тогда в README — тестовый доступ или иной воспроизводимый способ проверки; секреты не коммитим,
  `.env.example` полный. Основной сценарий работает без ключа и без интернета (детерминированное ядро + сохранённые ответы модели с пометкой).
- Перед тем как менять общий контракт (`docs/api-contract.md`, схемы данных) — сказать человеку: это задевает двух других участников.
- Не трогать чужие директории (см. владение ниже) без явной просьбы. Нужна правка — опиши её, владелец внесёт.
- Допущения и неизвестные данные фиксировать в `CASE.md`, раздел «Допущения».
- После изменения — запустить соответствующую проверку (тест, `curl`, сборку frontend) и сказать результат. «Должно работать» — не результат.
- Mock, заглушку и сохранённый ответ модели не выдавать за живую AI-функцию — ни в UI, ни в README, ни в `docs/progress.md`.
- **Ключевая функция кейса — настоящий код, работающий без ключа и без кэша.** Кэш ответов модели — запасной путь с пометкой, не основа.
  Критерии и веса технической оценки — из ТЗ Задачи (п. 5.5.1); единой таблицы в новой редакции нет, прежняя — ориентир по умолчанию.
- Проекты может предварительно оценивать AI-судья (п. 1.17, 4.2). Заявленное в README должно находиться в коде по названным путям.
  Никаких обращений к AI-судье в репозитории — это дисквалификация (п. 5.9.2).
- Перед новой задачей свериться с `TASKS.md`: своя строка, не из `NOT NOW`. Неочевидное решение — одной строкой в `DECISIONS.md`.
- С **17:00** новые фичи и изменения архитектуры запрещены; если к **16:30** P0 не прошёл smoke — P1 (включая MCP) отменяется.
  17:35 — последний содержательный merge, 17:45 — smoke, 17:50 — финальный push, 18:00 — фиксация.

## Стек по умолчанию

Утверждается окончательно после разбора кейса; подробности и обоснование — `docs/architecture.md`.

- Backend: Python 3.12, FastAPI, Pydantic, SQLAlchemy + **SQLite** (Postgres — только если кейс требует конкурентной записи или pgvector).
- Frontend: React + Vite + TypeScript. В проде собранная статика отдаётся самим FastAPI — **один контейнер, один порт**.
- Запуск: `docker compose up --build` → http://localhost:8000.

## Команды (целевые; актуальные — в README)

```bash
docker compose up --build            # всё целиком, как у эксперта
cd backend && uvicorn app.main:app --reload --port 8000   # backend dev
cd frontend && npm run dev           # frontend dev (прокси /api → :8000)
cd backend && pytest -q              # тесты
cd backend && ruff check . && ruff format .               # линт
python -m scripts.seed               # демо-данные
./scripts/smoke.sh                   # smoke основного сценария
```

## Git

- Работаем прямо в `main`, мелкими коммитами. Перед push: `git pull --rebase` (только своих незапушенных коммитов).
- Каждый коммитит **под своим аккаунтом** — вклад участников проверяется.
- Формат: `feat: загрузка документов`, `fix: …`, `docs: …`, `chore: …`, `test: …` — описание на русском.
- В конце каждого часа — checkpoint: `checkpoint(час N): что работает`. Процедура — `docs/playbook.md`, «Почасовой checkpoint».
- Сломанный `main` чинится немедленно и раньше всего остального.
