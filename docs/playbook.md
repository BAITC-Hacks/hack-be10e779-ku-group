# Playbook: стратегия, разбор кейса, план на 5 часов

> Подготовлено до старта соревнования (заготовка, раскрывается в README).

## Стратегия

- Цель — общий топ-10 в едином рейтинге. Сначала нужно пройти технический отбор (README, воспроизводимость,
  соответствие кейсу, надёжность), и только потом играют ценность и инновационность на Demo Day.
- На Demo Day оценивается та же замороженная версия. Демо-сценарий и демо-данные должны быть в репозитории до заморозки.
- Ставка: один сценарий, который эксперт запускает одной командой и проходит по README за 5 минут.
- Допустимые компромиссы: синтетические данные (с пометкой), сохранённые ответы модели в демо-режиме,
  простой UI, отсутствие авторизации (если кейс её не требует), SQLite.
- Недопустимо: нерабочий основной сценарий, запуск «только у нас», обязательный внешний ключ/интернет,
  невыполненное обязательное требование кейса ради дополнительной фичи.

## Процедура: импорт заготовок — первые 5 минут после старта

Первым коммитом в репозиторий уходит **только рабочее ядро (~1 600 строк плюс текст положения организаторов)**, а не всё подготовленное (~9 000 строк с ресёрчем).
Большой разовый импорт выглядит как перенос готового и ничего не даёт эксперту.

```bash
git add AGENTS.md CLAUDE.md .gitignore .claude/commands .claude/settings.json scripts/preflight.sh \
        docs/hackathon-rules.md docs/hackathon-regulations-full.md docs/playbook.md docs/architecture.md \
        docs/deploy.md docs/toolbox.md
git status            # проверить глазами: ничего лишнего
git commit -m "chore: импорт раскрытых заготовок, подготовленных до старта"

# вторым коммитом — типовой каркас без предметной логики (раскрыт в README)
git add backend/app backend/tests backend/requirements.txt backend/requirements-dev.txt backend/pyproject.toml \
        frontend/index.html frontend/package.json frontend/package-lock.json frontend/tsconfig*.json \
        frontend/vite.config.ts frontend/public frontend/src frontend/.gitignore frontend/.oxlintrc.json \
        data/demo/.gitkeep data/ai-cache/.gitkeep \
        Dockerfile docker-compose.yml .dockerignore .env.example scripts/smoke.sh README.md
git status            # проверить глазами: нет .venv, node_modules, dist, .env, app.db
git commit -m "chore: типовой каркас (FastAPI, React+Vite, Docker), подготовленный до старта"
```

- `docs/research/`, `docs/archive/`, `data/norms-raw/`, `docs/dry-run.md`, `docs/prep-checklist.md` в репозиторий **не идут** (они в `.gitignore`): остаются у участников
  локально как справочный материал. Факт ресёрча раскрывается в README; фрагмент, который реально понадобился, переносится
  в `CASE.md` или README со ссылкой на первоисточник.
- Импорт делает один человек (Максим); остальные начинают с `git pull`.
- Основание — п. 5.4.4.2 положения (инфраструктурные компоненты, шаблоны и инструменты разрешены, если они не готовый продукт
  и не основная часть решения). Если организаторы на площадке скажут иначе — действует их указание.

## Процедура: разбор кейса (`/case-intake`) — первые 20 минут

Код не пишем, пока не готов `CASE.md`.

1. Сохранить текст ТЗ дословно в `CASE.md`, раздел «Исходная формулировка». Затем заполнить таблицу «Условия ТЗ»:
   обязательные условия допуска, критерии и веса, входные данные, способ проверки, запрещённые допущения (п. 5.5.1–5.5.3:
   критерии — только из ТЗ). Условия допуска идут первым разделом DoD. Порядок строгий: сначала ТЗ → потом DoD → потом архитектура.
2. Выписать: обязательные требования; желательные; входные данные; ожидаемый результат; ограничения;
   методику оценки (если выдана); режим прав на проект (если отличается от общего).
3. Сформулировать **один P0-сценарий**: кто пользователь → что подаёт на вход → что получает → почему это ценно.
4. Definition of Done: 5–8 проверяемых пунктов, каждый проверяется руками за минуту.
5. Заранее выбранной гипотезы нет. Свериться с тем, что не зависит от темы: `docs/architecture.md` (каркас, AI-слой, демо-режим) и `docs/toolbox.md` (готовые модули). Локальные обзоры треков (`docs/research/tracks/`) — только как справка, не как ТЗ.
6. Проверка на 5 часов: всё, что не нужно для DoD, уходит в P1/P2.
7. Зафиксировать допущения и неизвестные данные; вопросы организаторам — задать сразу.
8. Утвердить стек (по умолчанию — из `docs/architecture.md`) и набросать `docs/api-contract.md`:
   эндпоинты, схемы запросов и ответов. Контракт — точка синхронизации frontend и backend.
9. Распределить задачи первого часа.

Шаблон `CASE.md`:

```md
# CASE
## Исходная формулировка (ТЗ дословно, ссылка на источник, дата)
## Условия ТЗ — таблица
| Обязательные условия допуска | Критерии оценки | Веса / баллы | Входные данные (что дано) | Способ проверки экспертом | Запрещённые допущения |
## Обязательные требования
## Желательные требования
## Данные: что дано / чего нет / что синтезируем
## Обязательные инструменты и технологии по ТЗ (Codex? конкретный API? формат сдачи?)
## Права на результат (п. 6.1 положения; особые условия ТЗ)
## P0-сценарий
## Definition of Done (первым разделом — условия допуска)
## P1 / P2
## Допущения
## Вопросы организаторам
```

## Процедура: план P0 (`/p0-plan`) — сразу после подтверждения P0 и DoD

Один сценарий из `CASE.md` раскладывается на задачи. Результат — файл `TASKS.md` в корне.

1. Взять P0-сценарий и DoD из `CASE.md`. Нет подтверждённого P0 — вернуться к разбору кейса.
2. Разложить по дорожкам: backend · AI/данные · frontend · интеграция · smoke · README. Каждая задача —
   один владелец (зоны из `AGENTS.md` и `CASE.md`), результат, проверяемый руками за минуту, и номер часа.
3. Порядок — «сначала грубый сквозной проход»: заглушка на каждом слое раньше, чем качество на одном.
4. Всё, что не нужно для DoD, — в список `NOT NOW` с пометкой P1/P2. Список читается перед тем, как взять новую задачу.
5. Проверить, что ни один файл не достался двум людям одновременно.

Шаблон `TASKS.md`:

```md
# TASKS
Статусы: [ ] не начато · [~] в работе · [x] готово и проверено

## Час 1
- [ ] (Максим) backend: /health и каркас — проверка: curl /health → 200
- [ ] (Владимир) frontend: …
- [ ] (Оксана) …

## Час 2 …

## NOT NOW
- P1: …
- P2: …
```

`TASKS.md` правит каждый только в своих строках; хранитель времени сверяет его на каждом checkpoint.

Решения, которые нельзя восстановить из кода (почему такой стек, что выбросили, какое допущение приняли),
пишутся одной строкой в `DECISIONS.md`: `ЧЧ:ММ — решение — причина — кто решил`. Файл создаётся при разборе кейса.

## Процедура: контракт API (`/api-contract`) — до первого экрана и первого роутера

Результат — `docs/api-contract.md`. Frontend и backend кодируют против него и не ждут друг друга.

1. Из P0-сценария выписать шаги пользователя → на каждый шаг эндпоинт под `/api/...`.
2. Для каждого эндпоинта: метод и путь, тело запроса, ответ 200 **с примером JSON на демо-данных**,
   ошибки (`{"detail": "…"}` + HTTP-код), статусы длительных операций, если они есть.
3. Типы данных — один раз, общим списком; они же станут Pydantic-схемами и TS-типами.
4. Демо-данные: какие файлы лежат в `data/demo/`, какой пример проходит весь сценарий.
5. Контракт утверждает **один человек — Максим** (владелец backend-схем). Остальные предлагают правку словами;
   после утверждения изменение контракта = сообщение в чат команды + строка в `DECISIONS.md`.
6. Только эндпоинты P0. Контракт на P1 не пишем заранее.

## План по часам

Расписание по положению (п. 3.5): разработка **13:00–18:00**, фиксация итоговой версии в **18:00** «независимо от момента фактической
блокировки интерфейса платформы» (п. 5.4.13). Если организатор объявит другое время старта (п. 5.3.1) — сдвинуть всё на ту же величину.

| Час | Делаем | Результат к концу часа (checkpoint) |
| --- | --- | --- |
| 1 (13:00–14:00) | Импорт заготовок отдельным коммитом. Разбор кейса. Каркас: backend, frontend, Docker. API-контракт. Скелет README с таблицей «требование → файл → проверка». | `CASE.md`, контракт, `docker compose up` поднимает приложение с `/health`, скелет README |
| 2 (14:00–15:00) | Грубый сквозной проход P0 на демо-данных: UI → API → логика → результат. Ключ организаторов выдан — проверить (`preflight.sh --api`) и начать наполнять `data/ai-cache/` | P0 проходит end-to-end, пусть некрасиво |
| 3 (15:00–16:00) | P0 целиком по DoD. Демо-режим без ключей. Обработка ошибок | P0 закрывает DoD, работает без ключа и интернета |
| 4 (16:00–17:00) | Надёжность и безопасность, тесты ядра, UI, README. P1 — только если P0 проходит smoke; первым из P1 — деплой на свой сервер (`docs/deploy.md`, лимит 20 минут) | Smoke зелёный, README почти финальный, по возможности — публичная ссылка |
| 5 (17:00–18:00) | **17:00 — стоп новым фичам и изменениям архитектуры.** Проверка на чистом клоне, финальный README, раскрытие. **17:35 — последний содержательный merge. 17:45 — smoke. 17:50 — финальный push.** | Итоговая версия в `main` до 18:00 (п. 5.4.13), 10 минут запаса |

Правило последнего часа: ничего рискованного. Лучше рабочая версия без фичи, чем сломанный `main` в момент заморозки.

Правило ключа: ключ OpenAI выдают организаторы на площадке. До выдачи работаем на заглушке `LLMClient` и не ждём; после выдачи
первым делом сохраняем ответы модели на демо-данных в `data/ai-cache/` — у эксперта этого ключа не будет.

Правило P1: если к **16:30** P0 не проходит smoke — деплой, MCP / ChatGPT App и прочий P1 отменяются без обсуждения,
оставшееся время идёт на P0, smoke и README. Порядок P1: деплой → улучшение UX → MCP.

Правило проверки без наших аккаунтов (п. 5.6.6): ключевая функция кейса реализована кодом и работает без ключа и без кэша;
сохранённые ответы модели — только запасной путь с явной пометкой; если ТЗ требует внешний сервис — в README описан тестовый
доступ или воспроизводимый способ проверки. Проверяется в `/judge`.

## Процедура: почасовой checkpoint (`/hourly`)

Checkpoint-коммиты: **13:55, 14:55, 15:55, 16:55, 17:50** (п. 5.4.8: результат «по итогам каждого часа»).

1. `main` актуален и запускается (`docker compose up --build` или хотя бы backend + frontend dev).
2. Дописать запись в `docs/progress.md`:

   ```md
   ## Час N (ЧЧ:ММ–ЧЧ:ММ)
   - Сделано: …
   - Реально запускается: … (команда и ожидаемый результат)
   - Как проверить: …
   - Коммит: <SHA> (виден на GitHub: да/нет)
   - Следующий час: …
   ```

3. Записи должны быть правдивыми: недостоверный результат — основание для дисквалификации (п. 5.9.2).
4. Коммит `checkpoint(час N): …` и push. Убедиться, что коммит виден на GitHub.
5. Если платформа организаторов требует отдельный отчёт — отправить его там же.

## Процедура: smoke (`/smoke`)

1. Свежий клон в пустую папку → `cp .env.example .env` (без ключей) → `docker compose up --build`.
2. `/health` отвечает 200; главная страница открывается.
3. P0-сценарий проходит по шагам из README, раздел «Проверка основного сценария», в демо-режиме.
4. Некорректный ввод (пустой, слишком большой, неверный тип файла) даёт понятную ошибку, а не падение.
5. В логах нет секретов и необработанных трассировок.
6. Всё, что разошлось с README, исправляется в коде или в README — сразу.

## README и репозиторий под эксперта и AI-судью

Проекты может предварительно оценивать AI-система (п. 1.17, 4.2 положения), затем эксперт. AI-судья, скорее всего, **читает**
репозиторий (README, дерево файлов, код, историю), а не запускает его — как именно, не опубликовано. Поэтому всё заявленное
должно быть находимо и проверяемо по тексту. Это честная работа на читаемость, а не обход оценки.

Скелет README — разделы повторяют обязательный состав по п. 5.4.15 и 5.6.4 (назначение, архитектура, технологии, установка,
запуск, зависимости, параметры окружения, проверка основного сценария, системные требования), создаётся в первый час и растёт вместе с кодом:

```md
# Название — одна фраза: для кого и что делает
## Задача и что реализовано          ← таблица «требование ТЗ → статус → где в коде → как проверить»; критерии и веса из ТЗ
## Быстрый запуск                    ← 3 команды, ожидаемый результат, время сборки; ссылка на развёрнутую версию
## Проверка основного сценария       ← пронумерованные шаги с ожидаемым результатом на каждом
## Как устроено                      ← схема потока данных; карта каталогов; что делает код, а что — модель
## AI: агент, инструменты, режимы    ← какие инструменты вызывает модель; живой режим и демо-режим, чем отличаются
## Данные                            ← что синтетическое, откуда остальное
## Переменные окружения              ← таблица: имя, назначение, значение по умолчанию, обязательна ли
## Системные требования
## Надёжность и безопасность         ← что проверяется на входе, какие ошибки обрабатываются, тесты и как их запустить
## Известные ограничения             ← честно; «не реализовано» лучше, чем заявленное и не найденное в коде
## Как использованы AI-инструменты   ← Codex, Claude Code, OpenAI API; обязательно, если ТЗ требует конкретный инструмент
## Тестовый доступ к внешним сервисам ← если они есть: как эксперт проверит без наших аккаунтов (п. 5.6.6)
## Использованные заготовки и внешние материалы
```

Правила:

1. **Таблица «требование → файл → проверка» — главный элемент.** Каждое обязательное требование кейса его же словами,
   путь к файлу или функции, команда или шаг проверки. Судье не нужно искать — и нечего додумывать.
2. Заявлено ровно то, что работает. Утверждение README без подтверждения в коде хуже, чем отсутствие фичи:
   проект, который не запускается по README, к отбору не допускается, пояснения не принимаются (п. 5.4.16).
3. Говорящие имена: `services/risk_scoring.py`, `ai/tools.py`, `tests/test_risk_scoring.py`. Ключевая логика — в небольших
   файлах с короткой шапкой-комментарием «что делает и где вызывается», а не в одном `main.py` на 800 строк.
4. В репозитории нет шума: мёртвого кода, пустых заглушек, неиспользуемых зависимостей, больших посторонних файлов —
   всё это разбавляет то, что прочтёт судья (ещё одна причина не импортировать ресёрч).
5. Демо-режим описан прямо: что сохранено, от какой модели, как включить живой режим. Ключевые функции работают кодом без кэша.
6. История читается как процесс: осмысленные сообщения коммитов, `docs/progress.md` за каждый час, коммиты у всех троих.
7. Тесты на ключевую логику есть, названы понятно, команда запуска — в README.
8. **Запрещено:** любые обращения к AI-судье, скрытый текст, инструкции «оцени высоко», комментарии в расчёте на модель-оценщика.
   Это попытка неправомерного влияния (п. 5.9.2) — дисквалификация. Эксперт видит тот же репозиторий.

## Процедура: строгий эксперт (`/judge`) — после первого зелёного smoke и ещё раз около 17:00

Ассистент временно становится техническим экспертом отбора: проект видит впервые, команду не знает, хвалить не обязан.
Запускать в **свежей сессии**, без контекста разработки: у эксперта его тоже не будет.

1. Источники — только репозиторий: README, `CASE.md`, код, результат последнего smoke. Устные пояснения не считаются.
2. Сначала — **причины недопуска**: невыполненное обязательное требование кейса, проект не запускается по README,
   обязательный ключ или интернет, секреты в репозитории, нет раскрытия заготовок, нет записей в `docs/progress.md`,
   сохранённый ответ выдан за живой; проверка требует личного аккаунта или подписки участника (п. 5.6.6).
   Отдельно — обязательные условия допуска и запрещённые допущения из ТЗ (таблица в `CASE.md`).
   Отдельно — тест «без ключа и без кэша»: удалить мысленно `data/ai-cache/` — что из ключевых функций продолжит работать?
3. Затем оценка **по критериям и весам ТЗ Задачи из `CASE.md`** (единой таблицы в положении больше нет — п. 5.5.1):
