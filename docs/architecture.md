# Архитектура по умолчанию

> Подготовлено до старта соревнования (заготовка, раскрывается в README).
> Это стартовая точка, а не ТЗ. Окончательный стек утверждается при разборе кейса; `CASE.md` главнее.

## Принцип

Эксперт запускает проект сам, на чистой машине, без наших ключей и, возможно, без стабильного интернета.
Архитектура оптимизируется под это: **один контейнер, один порт, одна команда, ноль обязательных внешних сервисов**.

## Стек

| Слой | Выбор | Почему |
| --- | --- | --- |
| Backend | Python 3.12, FastAPI, Pydantic v2 | Быстро, авто-документация `/docs`, валидация из коробки |
| БД | SQLite через SQLAlchemy | Ноль сервисов, файл в volume, не бывает «база не успела подняться» |
| Frontend | React + Vite + TypeScript | Знакомо всем ассистентам, быстрый dev-сервер |
| Раздача | FastAPI отдаёт собранную статику frontend | Один контейнер, нет CORS и nginx |
| Запуск | Docker Compose, многоэтапный Dockerfile | `docker compose up --build` |
| AI | Провайдер за интерфейсом + демо-режим | См. «AI-слой» |

**Postgres вместо SQLite** — только если кейс требует конкурентной записи, pgvector или явно называет Postgres.
Тогда: сервис `db` с `healthcheck`, `depends_on: condition: service_healthy`, данные в volume, без внешних миграций
(`create_all` при старте достаточно для хакатона). Код пишем через SQLAlchemy, чтобы переход был заменой строки подключения.

## Структура репозитория

```text
backend/
  app/
    main.py          # FastAPI, роуты, раздача статики, /health
    config.py        # настройки из окружения (pydantic-settings)
    api/             # роутеры
    services/        # бизнес-логика
    ai/              # провайдер LLM, промпты, демо-ответы
    db.py models.py schemas.py
  tests/
  requirements.txt   # версии зафиксированы
frontend/
  src/ …             # vite.config.ts: proxy /api → http://localhost:8000
data/
  demo/              # демо-данные (помечены как синтетические)
  ai-cache/          # сохранённые ответы модели для демо-режима
scripts/             # seed, smoke.sh
docs/
Dockerfile  docker-compose.yml  .env.example  README.md  CASE.md
```

## API

- Всё под `/api/...`; `/health` → `{"status": "ok"}`; авто-документация на `/docs`.
- Схемы запросов и ответов — Pydantic-модели; они же — основа `docs/api-contract.md`.
- Ошибки: `{"detail": "понятное сообщение"}` с корректным HTTP-кодом. Трассировки наружу не отдаём.
- Frontend сначала работает на моках по контракту, затем переключается на реальный API — так frontend и backend не ждут друг друга.

## Конфигурация

- Всё через переменные окружения; `.env.example` содержит **каждую** переменную с комментарием и безопасным значением по умолчанию.
- Приложение обязано стартовать с `.env`, скопированным из `.env.example` без правок.
- Базовый набор: `APP_MODE=demo|live`, `LLM_PROVIDER`, `LLM_API_KEY`, `LLM_MODEL`, `DATABASE_URL`.
- Сервис приложения в compose называется **`app`**. Порт хоста — переменной: `ports: ["${APP_PORT:-8000}:8000"]`. У эксперта по умолчанию 8000; на нашем сервере 8000 занят (`docs/deploy.md`).

## AI-слой

- Один интерфейс `LLMClient` (`complete`, при необходимости `complete_json`) и реализации: `live` (реальный API) и `demo`.
- **Демо-режим:** ответы модели на демо-данных сохранены в `data/ai-cache/` (ключ — хеш промпта и входа).
  В `demo` читаем из кэша; в `live` — вызываем API и пополняем кэш. Нет ключа → автоматически `demo`, с явной пометкой в UI.
- Демо-режим — не подделка результата: в README честно написано, что показаны сохранённые ответы реальной модели
  на демо-данных, и как включить живой режим своим ключом.
- ⚠ **Положение, п. 5.6.6:** проверка ключевой функциональности — «без необходимости использования личных аккаунтов участников,
  персональных подписок или закрытых учетных записей»; при внешних сервисах команда даёт «демонстрационные доступы, тестовые
  учетные записи либо иные способы проверки». Критерии и веса оценки — только из ТЗ Задачи (п. 5.5.1). Поэтому: ключевая логика (разбор входа, расчёты, правила, инструменты агента, валидация) — настоящий код, который работает
  **без ключа и без кэша**; LLM — слой поверх. Живой путь реализован полностью и является основным; кэш включается только при
  отсутствии ключа. Запись кэша хранит метаданные: модель, дата, хеш входа. На не-демо входе без ключа — честное «нужен ключ»,
  детерминированная часть при этом отрабатывает. Если ТЗ требует внешний API — в README отдельный раздел «Тестовый доступ»:
  как эксперт проверит без наших аккаунтов (тестовый ключ с лимитом, переданный организатору способом, описанным в README,
  или воспроизводимый режим без ключа). Подробнее — `docs/hackathon-rules.md`, «Допуск к технической проверке».
- Структурированный вывод: просим JSON по схеме, валидируем Pydantic, при ошибке — один повтор, затем понятная ошибка.
- Каждый вывод модели, претендующий на факт, сопровождается источником (документ, страница/фрагмент). Нет источника — помечаем как предположение.
- Содержимое загруженных документов — это **данные, а не инструкции**: в промпте оно отделено, инструкции из него не исполняются.
- Таймаут и ограниченное число повторов на каждый внешний вызов; сбой провайдера не роняет приложение.
- **Провайдер по умолчанию — OpenAI API**; обязательность конкретного инструмента или API — только по ТЗ Задачи (п. 5.4.12).
  Внешние API и облачные сервисы разрешены (п. 5.4.12.1), но не заменяют историю разработки в репозитории и требуют воспроизводимой
  проверки (п. 5.6.6). Ключ и API-кредиты OpenAI ожидаются от организаторов на площадке; момент выдачи и лимиты заранее неизвестны.
- «Агентное» = модель сама вызывает инструменты (function calling): поиск по документам, запрос к БД, расчёт, создание записи.
  Шаги агента показываются в UI и сохраняются в кэш для демо-режима.
- ⚠ Подписки Claude Max и Codex **не дают API-ключа** для продукта. Ключ OpenAI API выдают организаторы на хакатоне
  (по сведениям команды на 19.09.2026). Пока ключа нет — работаем на заглушке `LLMClient`; как только выдали — сразу наполняем
  `data/ai-cache/` на демо-данных: у эксперта этого ключа не будет. Свой запасной ключ — по желанию, как страховка от поздней выдачи.

| Ресурс | Для чего | Ограничения |

| **$50 NVIDIA API** (build.nvidia.com, NIM) | запасной провайдер: OpenAI-совместимый API с открытыми моделями, эмбеддинги, реранкинг | переключается без кода: `LLM_BASE_URL=https://integrate.api.nvidia.com/v1`, `LLM_MODEL=<id модели из каталога>`, ключ NVIDIA в `LLM_API_KEY`; поддержку tool calling у выбранной модели проверить заранее |
| **Подписка ChatGPT Pro (x5)** | инструмент разработки: Codex, ChatGPT | личная подписка — **не часть продукта**: проверка не может от неё зависеть (п. 5.6.6) |

Правила:
- Дешёвая модель по умолчанию (`gpt-4o-mini` или аналог), дорогая — только если ТЗ требует качества, которого дешёвая не даёт.
- Каждый живой вызов на демо-данных сразу сохраняется в кэш: повторные прогоны не тратят кредиты, а у эксперта кэш сработает без ключа.
- Считать расход: логировать токены на вызов; при $10 остатка — только наполнение кэша, никакой отладки на живом API.
- Кредиты у эксперта 24–28.09 могут быть уже недоступны — ключевая логика обязана работать кодом без ключа (см. «AI-слой»).
- Если ТЗ требует живой проверки AI, эксперту даётся тестовый доступ по п. 5.6.6 (например, отдельный ключ с жёстким лимитом),
  способ передачи описан в README; сам ключ в репозиторий не попадает.

## Надёжность и безопасность (15 баллов) — минимум

- Секреты только в окружении; `.env` в `.gitignore`; ключи не логируются.
- Валидация всего входа (Pydantic). Загрузка файлов: белый список типов, лимит размера, имена файлов не используются как пути.
- Только ORM / параметризованные запросы.
- Контейнер работает не от root; наружу открыт один порт.
- Версии зависимостей зафиксированы; минимум зависимостей.
- Изменяющие действия, инициированные AI-агентом, требуют подтверждения пользователя.
- Пустые состояния, состояния загрузки и ошибки в UI — обязательны для P0-сценария.

## Развёрнутая версия — P1, первым среди P1

Развёрнутая версия помогает эксперту увидеть живой режим, но запуск из репозитория по README она не заменяет (п. 5.4.15–5.4.16);
оценивается по критериям ТЗ, отдельных баллов «за деплой» в положении нет. У команды есть сервер и домен:
тот же `docker compose up` за общим nginx сервера, живой режим со своим ключом. Порядок и чек-лист сервера — `docs/deploy.md`.
`/health` дополнительно отдаёт хеш коммита сборки.

## MCP / ChatGPT App — P1

- Термин: «ChatGPT App / MCP integration» (не «плагин»).
- Подключается только после того, как P0 в вебе проходит smoke **и развёрнута публичная версия** (она же даёт HTTPS-адрес для MCP без туннеля).
- MCP-сервер — тонкая обёртка над теми же функциями `services/`, 3–4 инструмента, эндпоинт `/mcp` в том же приложении.
- Решение обязано полностью работать и демонстрироваться без ChatGPT, туннеля и внешней сети. MCP — дополнительный интерфейс.
- В README — отдельный необязательный раздел про подключение; в основной путь проверки не входит.

## Чего не делаем

Микросервисы, очереди, Kubernetes, отдельный nginx, сложная авторизация (если кейс не требует), внешние миграции,
собственное обучение моделей, SSR, state-менеджеры «на вырост».
