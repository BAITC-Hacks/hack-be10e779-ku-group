## Репозиторий и история (п. 5.4.7, 5.4.9, 5.4.11, 5.9.2)

- Репозиторий создан организатором через edu.astanahub.com; с момента старта — «единственный основной рабочий репозиторий Проекта»
  с «подтверждаемой историей разработки» (п. 5.4.11).
- Организатор проверяет «историю разработки, репозиторий, метаданные файлов, работоспособность проекта и фактический вклад
  каждого участника» (п. 5.4.7) — коммитит каждый, под своим аккаунтом.
- Внешние API, облачные платформы, онлайн-сервисы разработки разрешены, но «не освобождают от требований по ведению
  разработки в Репозитории» (п. 5.4.12.1).
- Наше правило: до 13:00 в репозиторий ничего не пушим; заготовки импортируем после старта отдельным подписанным коммитом —
  только рабочее ядро, без ресёрча (`docs/playbook.md`, «Импорт заготовок»).

## Ежечасные результаты (п. 5.4.8, 5.9.2)

Каждая команда «обязана иметь промежуточный результат по итогам каждого часа»: изменения в коде или репозитории, функционал,
прототип, дизайн, схема архитектуры, настроенная модель, тестирование, подготовленные данные «или иное подтверждение
фактического прогресса». Отсутствие результата за любой час — основание для дисквалификации (п. 5.9.2).
Способ подтверждения положение не описывает.

Наше правило: checkpoint-коммит в **13:55, 14:55, 15:55, 16:55, 17:50** + запись в `docs/progress.md`: что сделано /
что реально запускается / как проверить / SHA коммита / план на следующий час.

## Допуск к технической проверке — жёсткий gate (п. 5.4.15–5.4.16, 5.6.3–5.6.6)

- README обязан содержать: назначение решения; архитектуру; технологии; установку; запуск; зависимости; параметры окружения;
  порядок проверки основного сценария (п. 5.4.15) — «пошаговая инструкция», включая системные требования (п. 5.6.4).
- **«Если итоговую версию Проекта не удаётся запустить по инструкциям, размещённым в Репозитории, Команда не допускается
  к дальнейшему отбору. Дополнительные пояснения и исправления не принимаются»** (п. 5.4.16, 5.6.5).
  (Прежняя редакция допускала пояснения экспертам — **устарело**.)
- Проверка ключевой функциональности — «без необходимости использования личных аккаунтов участников, персональных подписок
  или закрытых учетных записей»; для внешних сервисов и API команда обязана дать «демонстрационные доступы, тестовые учетные
  записи либо иные способы проверки» (п. 5.6.6).
- Наше правило: секреты не коммитим; `.env.example` со всеми переменными; способ безопасной передачи тестового доступа
  (если он нужен) описан в README отдельно; ключевая логика работает без ключа — см. `docs/architecture.md`.

## Дисквалификация (п. 5.9.2; без предупреждения — п. 5.9.3)

- нет подтверждённого промежуточного результата за любой отчётный час;
- отсутствие на площадке без разрешения; непройденный check-in или иные процедуры учёта присутствия;

- проект «полностью или преимущественно» создан третьими лицами без раскрытия;
- вмешательство в платформы, сети, проекты других команд; вредоносный код, попытки несанкционированного доступа;
- неэтичное поведение; давление на экспертов, судей, партнёров, организатора, подкуп, неправомерное влияние;
- нарушение правил площадки; отказ выполнять законные требования или предоставлять документы;
- иные действия против справедливости, равенства условий и достоверности результатов.

Апелляций и повторной оценки нет (п. 5.10.3–5.10.4); исправляются только арифметические, технические и редакционные ошибки (п. 5.10.6).

## Интеллектуальные права (п. 6.1)

> ⚠ Изменилось. Прежняя формулировка «исключительные права остаются у авторов, организатору — узкая лицензия» **устарела**.

Участники предоставляют организатору право использования Результатов (код, алгоритмы, модели, дизайн, документация, презентации)
«безвозмездно, без ограничения по территории и сроку действия» (п. 6.1.4), «включая воспроизведение, публикацию, модификацию,
адаптацию, распространение и передачу третьим лицам» (п. 6.1.3), в целях, связанных с хакатоном, развитием технологий и экосистемы.
Личные неимущественные права авторов охраняются законом (п. 6.1.6). Участник гарантирует права на материалы, соблюдение лицензий
и раскрытие сторонних компонентов (п. 6.1.5, 6.1.7) — при нарушении возмещает убытки солидарно.
Следствия: в проект не попадает код и данные, которые нельзя передать организатору на таких условиях; раздел раскрытия — точный.
